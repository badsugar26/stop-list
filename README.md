# Стоп-лист смены

Тестовое задание **Junior Fullstack Developer**
**React · Express · TypeScript**

Стоп-лист — сервис для управления блюдами, временно снятыми с продажи.

Повар может поставить блюдо в стоп-лист, указав причину и срок. Зал получает актуальный список блюд, недоступных для заказа, и видит время их предполагаемого возврата.

**Демо:** будет добавлено после деплоя.

**Репозиторий:** https://github.com/badsugar26/stop-list

---

## Стек

* **Backend:** Node.js 20+, Express 4, TypeScript
* **Frontend:** React 18, Vite, TypeScript
* **Хранилище:** in-memory repository за интерфейсом
* **Валидация:** отдельный middleware с ручной проверкой входных данных

Реальная БД не подключена — использование in-memory хранилища допускается условиями задания.

## Запуск локально

Требуется **Node.js 20+** и **npm**.

### 1. Установка зависимостей

Из корня проекта:

```bash
npm install

cd server
npm install

cd ../client
npm install

cd ..
```

### 2. Настройка переменных окружения

```bash
cp .env.example .env
cp .env.example server/.env
```

### 3. Запуск

Запустить frontend и backend одной командой:

```bash
npm run dev
```

После запуска:

* Frontend: http://127.0.0.1:5173
* Backend: http://localhost:3000

Отдельный запуск:

```bash
npm run dev:server   # только backend
npm run dev:client   # только frontend
```

## Архитектура

Backend разделён на слои:

```text
routes → services → repositories → domain
 HTTP      логика       данные       типы
```

### `domain/`

Содержит доменные типы, чистые функции и ошибки:

* `Dish`
* `StopListEntry`
* `StopListEntryView`
* `isActive()`
* `getStatus()`
* `minutesLeft()`
* `toView()`
* `NotFoundError`
* `ConflictError`
* `ValidationError`

Доменный слой не зависит от Express, HTTP или конкретной БД.

### `repositories/`

Доступ к данным осуществляется через интерфейсы:

* `DishRepo`
* `StopListRepo`

Текущая реализация — in-memory.

Благодаря этому источник данных можно заменить, например, на Prisma + SQLite, не изменяя бизнес-логику сервисов.

### `services/`

Содержит бизнес-логику стоп-листа.

Сервисный слой не знает о `req`, `res` и HTTP. Он работает с доменными сущностями и репозиториями.

Текущее время передаётся как зависимость:

```ts
now: () => Date
```

Это позволяет тестировать поведение на границе срока действия записи.

### `routes/`

Тонкий HTTP-слой:

1. получает данные из запроса;
2. вызывает сервис;
3. возвращает HTTP-ответ.

Бизнес-логика в routes не находится.

### `middleware/`

Содержит:

* валидацию входных данных;
* `asyncHandler`;
* единый `errorHandler`.

Все ошибки API приводятся к единому формату в одном месте.

## API

Формат ошибки:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Описание ошибки"
  }
}
```

| Метод   | Endpoint                    | Назначение                 | Успех | Ошибки              |
| ------- | --------------------------- | -------------------------- | ----- | ------------------- |
| `GET`   | `/api/health`               | Проверка состояния API     | `200` | —                   |
| `GET`   | `/api/dishes`               | Получение справочника блюд | `200` | —                   |
| `POST`  | `/api/stop-list`            | Поставить блюдо в стоп     | `201` | `404`, `409`, `422` |
| `GET`   | `/api/stop-list`            | Получить активные записи   | `200` | —                   |
| `PATCH` | `/api/stop-list/:id/return` | Досрочно вернуть блюдо     | `200` | `404`, `409`        |
| `GET`   | `/api/stop-list/history`    | Получить историю           | `200` | `422`               |

### Фильтрация активного стоп-листа

```http

```

Поддерживаемые категории:

* `Кухня`
* `Бар`
* `Десерты`

### Пагинация истории

```http
GET /api/stop-list/history?limit=20&offset=0
```

## Принятые архитектурные решения

### In-memory хранилище

Данные хранятся в памяти процесса и сбрасываются после перезапуска сервера.

Репозитории определены через интерфейсы, поэтому бизнес-логика не зависит от конкретного способа хранения данных.

Замена in-memory реализации на Prisma/SQLite потребует реализации тех же интерфейсов без изменения сервисного слоя.

### Разделение ответственности

Каждый слой отвечает только за свою задачу:

* `routes` — HTTP;
* `services` — бизнес-правила;
* `repositories` — работа с данными;
* `domain` — типы и чистые функции.

Это позволяет не смешивать HTTP-логику с бизнес-логикой и упрощает дальнейшее развитие проекта.

### Время как зависимость

Сервис получает функцию:

```ts
now: () => Date
```

Вместо прямого вызова `new Date()` внутри бизнес-логики.

Это позволяет контролировать время в тестах и проверять поведение на границе `expiresAt`.

### Истечение срока без фоновых задач

Отдельная cron-задача для завершения стоп-листа не используется.

Запись считается активной, пока:

```ts
expiresAt > now
```

После истечения срока `isActive()` возвращает `false`.

При этом `returnedAt` остаётся `null`, поскольку истечение срока и ручной досрочный возврат — разные состояния.

### Единый обработчик ошибок

Формирование HTTP-ответов с ошибками централизовано в:

```text
middleware/errorHandler.ts
```

Доменные ошибки содержат код и HTTP status code.

Необработанные ошибки возвращаются как `500`, без передачи stack trace клиенту.

### Валидация

Валидация входных данных вынесена в отдельный middleware.

Zod/Joi не используются — решение принято в пользу минимального количества зависимостей и фокуса на архитектуре базового решения.

## Что можно улучшить

При наличии дополнительного времени проект можно развить в следующих направлениях:

### База данных

Добавить Prisma + SQLite:

* модели `Dish` и `StopListEntry`;
* миграции;
* seed;
* реализации репозиториев поверх Prisma.

### Схемная валидация

Заменить ручную валидацию на Zod:

```ts
const schema = ...
type Input = z.infer<typeof schema>
```

Это позволит одновременно валидировать входные данные и получать TypeScript-типы из схем.

### Тестирование

Добавить Vitest для бизнес-логики.

Основные сценарии:

* `isActive()` на границе срока;
* минимальная и максимальная продолжительность стопа;
* повторная постановка блюда в стоп;
* возврат уже неактивной записи;
* корректное определение статусов.

Дополнительно — интеграционные тесты HTTP API.

### Frontend data fetching

Заменить самописный `useStopList` на TanStack Query.

Это даст:

* автоматическую инвалидацию кэша;
* retry;
* stale-time;
* удобное управление состояниями загрузки и мутаций.

### История в интерфейсе

Добавить UI для просмотра истории стоп-листа с пагинацией.

API для истории уже реализован.

### UX

Перенести форму постановки блюда в модальное окно и дополнительно адаптировать интерфейс для мобильных устройств.

### Docker

Добавить `docker-compose.yml` для запуска проекта одной командой.

### CI

Добавить GitHub Actions с проверками:

```text
lint
typecheck
tests
```

на каждый `push` и `pull request`.

   Заменить самописный `useStopList` на TanStack Query для автоматической инвалидации кэша после мутаций, управления состояниями запросов, retry и `staleTime`.

6. **Улучшить UX формы постановки в стоп.**

7. **Добавить Docker Compose.**
   Подготовить `docker-compose.yml` для запуска frontend и backend одной командой.

8. **Настроить CI через GitHub Actions.**
   Добавить автоматические проверки линтера, TypeScript (`typecheck`) и тестов на каждый `push` и `pull request`.
